# C2 — QA verification

## Inputs

- Bootstrap per `_shared.md`. `WORKTREE_PORT` comes from `PORT=` in `.env` (re-run
  `bin/worktree-port --assign .env` only if that port is now taken by another server).

**Parallel:** you are the **follower** of the C1 ‖ C2 pair (`_shared.md` → Parallel pairs). C1 is
writing and fixing system specs right now on the test DB. Steps 1–4 (server, dev-DB migrate, QA
document, QA execution, screenshots) run immediately — they touch only the dev DB, `docs/qa-plans/`,
`docs/bug-reports/`, and `tmp/`. **Before Step 5** (any bug fix, regression spec, or commit) and
before writing the state file, wait for C1's Phase Log box (the poll in `_shared.md`). If C1's
commits changed any `app/` file, re-execute the scenarios whose `Verifies:` ACs touch those areas
before fixing anything — C1 may already have fixed the bug. Never run rspec against the test DB
until C1 is done.

## Steps

### Step 1: Start the dev server (detached — it stays up for review after the pipeline)

`bin/dev` reads the port from `PORT=` in `.env`, so no Procfile edits are needed.

```bash
WORKTREE_PORT="$(grep -E '^PORT=' .env | cut -d= -f2)"
BASE_URL="http://localhost:${WORKTREE_PORT}"
if curl -sk -o /dev/null "$BASE_URL"; then
  echo "Dev server already running on ${WORKTREE_PORT} (resumed run) — reusing it"
else
  mkdir -p log
  nohup bin/dev </dev/null >log/dev-server.log 2>&1 &
  disown
fi
for i in $(seq 1 30); do
  STATUS=$(curl -sk -o /dev/null -w "%{http_code}" "$BASE_URL" 2>/dev/null)
  if [ "$STATUS" = "200" ] || [ "$STATUS" = "302" ]; then echo "Dev server ready on ${WORKTREE_PORT}"; break; fi
  sleep 1
done
```

If it isn't up after 30 s: `tail -20 log/dev-server.log`, try `bundle install && bin/rails db:migrate`,
retry; still failing → skip QA and note "QA skipped: dev server unavailable" in the state file.

### Step 2: Migrate the isolated database

```bash
bin/rails db:migrate 2>&1 | tail -10     # <app>_development${DB_SUFFIX} — the main repo's DB is never touched
```

### Step 3: Create the QA document

```
/create-qa-document --base-url=http://localhost:${WORKTREE_PORT}
```

- It analyzes `git diff main...HEAD` and reads the contract: rows become scenarios tagged
  `**Verifies:** AC-n`; `guard` rows become **negative** scenarios asserting the absence literally.
- Check the plan's **AC Coverage** table: every `browser` / `browser+spec` AC (every **Must**,
  including guards) should have a scenario. Anything under **Uncovered** → add a scenario now (edit
  the QA plan directly) — an uncovered Must AC fails the Acceptance Gate in C3.
- Verify the document's `**Base URL:**` is `http://localhost:${WORKTREE_PORT}`.

### Step 4: Execute QA

```
/execute-qa docs/qa-plans/{feature-name}-*.md
```

`/execute-qa` reads the base URL from the QA plan — all browser navigation uses the worktree port,
never the main checkout port. Do not start a second server. Follow its snapshot discipline (depth 5, `target:`,
`filename:` for big pages) — this is the phase most at risk of blowing its context.

**Keep screenshots for the PR:** during the happy-path scenarios capture **2–4 screenshots of the
feature's key screens** (the primary flow a reviewer wants to see — not error states) into
`tmp/pr-screenshots/` with descriptive kebab-case names (e.g. `client-list-with-filters.png`). Keep
each under ~1MB (default viewport PNG is fine). Delete every other screenshot the run created.

### Step 5: Handle QA results

**All scenarios PASS** → CHECKPOINT.

**Scenarios FAIL with bugs:**
1. Read each bug report; fix the bugs (directly, or via a worker per `_shared.md` when a fix spans
   several files — pass the bug report verbatim).
2. **Write a regression spec for every bug fixed** — one that fails on the pre-fix code and passes on
   the fix. Prefer the cheapest layer (model/service/controller/component); a system spec only if the
   bug is inherently browser-level (allowed now — C1 is done).
3. Commit the fixes with their regression specs (`fix: <what> found by QA for ${FEATURE_NAME}`).
4. Re-execute the failed scenarios only.
5. **Maximum 2 bug-fix cycles** — still failing → record under "Known Issues (QA)".

Do **not** stop the dev server or close the browser: C3 may execute additional scenarios.

## CHECKPOINT

Update the state file: Phase Log C2 checked; Artifacts with the QA plan path, the QA results/bug
report locations, and fix commit hashes; Results with scenarios passed/failed, bugs found/fixed,
screenshots kept (names); Known Issues (QA).

## RETURN

```
C2 DONE
SERVER: http://localhost:<port> (running)
QA PLAN: <path>  RESULTS: <passed>/<total> scenarios; AC coverage: <covered>/<browser ACs>
BUGS: <found> found, <fixed> fixed (<commit hashes>); open: <none | list>
SCREENSHOTS: <n> in tmp/pr-screenshots/
```
